第 11 章 デバッグと性能計測

並行処理や並列処理を使ったプログラムは、実行の順序が毎回変わるため、不具合の原因を見つけにくい。また、「速くなったつもり」で実際には速くなっていないこともある。この章では、性能の計測、デバッグ、テストの方法を説明する。

性能の計測

経過時間の計測

並行処理や並列処理の効果は、経過時間で評価する。経過時間の計測には time.perf_counter() を使う。time.time() は時計の時刻を返すため、時刻の補正によって値が変わることがあり、計測には向かない。

1import time
2
3start = time.perf_counter()
4run()  # 計測したい処理
5elapsed = time.perf_counter() - start
6print(f"{elapsed:.2f} 秒")

第 2 章 基本概念 で説明したとおり、time.process_time() で CPU 時間も測ると、処理が CPU バウンドか I/O バウンドかを判断できる。経過時間に比べて CPU 時間が小さければ I/O バウンド、ほぼ等しければ CPU バウンドである。

計測するときは、次の点に注意する。

  • 何度か実行して比べる。1 回目は、ファイルのキャッシュやモジュールの読み込みの影響で遅くなることがある。他のプログラムの影響も受けるため、複数回実行して傾向を確認する。

  • 起動の時間を含めるかどうかを意識する。ProcessPoolExecutor の起動には時間がかかる。第 6 章 プロセスによる並列処理 の chunksize.py のように、起動を除いた時間を測りたい場合は、先に一度使ってから計測する。実際の利用場面で毎回プロセスを起動するなら、起動の時間も含めて評価する。

  • 実際のデータに近い条件で測る。少量のデータでは並列化の負荷が目立ち、大量のデータでは効果が目立つ。

ボトルネックの特定

プログラムのどこに時間がかかっているかを調べるには、プロファイラーを使う。標準ライブラリの cProfile は、関数ごとの呼び出し回数と実行時間を集計する。

python -m cProfile -s cumtime main.py

-s cumtime は、その関数から呼び出した関数の時間も含めた累積時間で並べ替える指定である。時間の大半が socket の受信や time.sleep() などで使われていれば I/O バウンド、自分で書いた計算の関数で使われていれば CPU バウンドと判断できる。

ログによる追跡

並行処理の不具合を調べるときは、どのスレッドやタスクが、いつ、何をしたかを記録すると原因を絞り込みやすい。logging モジュールは、ログの書式にスレッド名やプロセス ID を含められる。logging モジュールはスレッドセーフなので、複数のスレッドから同時に呼び出しても出力が混ざらない。

1import logging
2
3logging.basicConfig(
4    level=logging.DEBUG,
5    format="%(asctime)s %(processName)s %(threadName)s %(message)s",
6)

asyncio のタスクには、create_task(coro, name="download-1") のように名前を付けられる。実行中のタスクの名前は asyncio.current_task().get_name() で取得できる。Python 3.12 以降では、ログの書式に %(taskName)s を指定してタスク名を出力することもできる。

asyncio のデバッグモード

asyncio には、よくある誤りを検出するデバッグモードがある。デバッグモードでは、次のような問題が警告として出力される。

  • 1 回の実行に一定時間（既定では 0.1 秒）以上かかり、イベントループをブロックした処理

  • await されなかったコルーチンが作られた場所

  • 別のスレッドから、スレッドセーフでない asyncio の API が呼ばれたこと

デバッグモードは、asyncio.run(main(), debug=True) と書くか、環境変数 PYTHONASYNCIODEBUG=1 を設定するか、python -X dev で Python の開発モードを有効にすると使える。

debug_mode.py

 6import asyncio
 7import time
 8
 9
10async def well_behaved() -> None:
11    await asyncio.sleep(0.3)  # イベントループに制御を返しながら待つ
12
13
14async def badly_behaved() -> None:
15    time.sleep(0.3)  # イベントループごと止めてしまう
16
17
18async def main() -> None:
19    async with asyncio.TaskGroup() as group:
20        group.create_task(well_behaved(), name="well_behaved")
21        group.create_task(badly_behaved(), name="badly_behaved")
22
23
24if __name__ == "__main__":
25    # 環境変数 PYTHONASYNCIODEBUG=1 を設定するか、python -X dev で実行しても同じ効果がある
26    asyncio.run(main(), debug=True)

実行すると、badly_behaved() がイベントループを 0.3 秒ブロックしたことが警告される（読みやすさのため、ファイルのパスを省略している）。

Executing <Task finished name='badly_behaved' coro=<badly_behaved() done, defined at ...\debug_mode.py:14> result=None created at ...\asyncio\taskgroups.py:196> took 0.301 seconds

デバッグモードは処理が遅くなるため、開発中やテストのときに使い、本番の環境では無効にする。

実行中のタスクを調べる

Python 3.14 以降では、実行中の Python のプロセスについて、asyncio のタスクの状態を外から調べられる。プログラムが応答しなくなったときに、どのタスクが何を待っているかを確認するのに役立つ。

表 22 タスクを調べるコマンド

コマンド

説明

python -m asyncio ps PID

プロセス PID のタスクを一覧表示する。

python -m asyncio pstree PID

タスクの待ち合わせの関係を木構造で表示する。

次のサンプルは、タスクを入れ子に作成し、60 秒間待ち続ける。

inspect_tasks.py

 9import asyncio
10import os
11
12
13async def download(name: str) -> None:
14    await asyncio.sleep(60)
15
16
17async def crawler(name: str) -> None:
18    async with asyncio.TaskGroup() as group:
19        for page in range(2):
20            group.create_task(download(f"{name}-{page}"), name=f"download-{name}-{page}")
21
22
23async def main() -> None:
24    print(f"PID: {os.getpid()}（60 秒後に終了する）")
25    async with asyncio.TaskGroup() as group:
26        group.create_task(crawler("A"), name="crawler-A")
27        group.create_task(crawler("B"), name="crawler-B")
28
29
30if __name__ == "__main__":
31    asyncio.run(main())

このサンプルを実行したまま、別の端末で python -m asyncio pstree PID を実行すると、次のように表示される（読みやすさのため、ファイルのパスを省略し、crawler-B 以下を省略している）。

└── (T) Task-1
    └──  main ...\inspect_tasks.py:25
        └──  TaskGroup.__aexit__ ...\asyncio\taskgroups.py:72
            └──  TaskGroup._aexit ...\asyncio\taskgroups.py:121
                ├── (T) crawler-A
                │   └──  crawler ...\inspect_tasks.py:18
                │       └──  TaskGroup.__aexit__ ...\asyncio\taskgroups.py:72
                │           └──  TaskGroup._aexit ...\asyncio\taskgroups.py:121
                │               ├── (T) download-A-0
                │               │   └──  download ...\inspect_tasks.py:14
                │               │       └──  sleep ...\asyncio\tasks.py:704
                │               └── (T) download-A-1
                │                   └──  download ...\inspect_tasks.py:14
                │                       └──  sleep ...\asyncio\tasks.py:704
                └── (T) crawler-B
                    （省略）

(T) はタスクを表す。main() のタスク（Task-1）が 2 つの crawler のタスクを待ち、それぞれの crawler が 2 つの download のタスクを待っていること、download のタスクが asyncio.sleep() で止まっていることが分かる。タスクに名前を付けておくと、このような出力が読みやすくなる。

プログラムが止まったときの調査

デッドロックなどでプログラムが止まった場合は、各スレッドがどこで止まっているかを調べる。標準ライブラリの faulthandler モジュールを使うと、全スレッドのスタックトレースを出力できる。

1import faulthandler
2import sys
3
4# 60 秒経過するたびに、全スレッドのスタックトレースを標準エラー出力に書き出す
5faulthandler.dump_traceback_later(60, repeat=True, file=sys.stderr)

python -X faulthandler で実行すると、プログラムが異常終了したときにもスタックトレースが出力される。

非同期処理のテスト

コルーチンをテストするには、標準ライブラリの unittest.IsolatedAsyncioTestCase を使う。このクラスを継承したテストクラスでは、テストメソッドを async def で定義でき、テストごとに新しいイベントループで実行される。

次のサンプルでは、失敗したときに再試行するコルーチン関数 retry() をテストする。

test_retry.py

 8import asyncio
 9import unittest
10from collections.abc import Awaitable, Callable
11from typing import TypeVar
12
13T = TypeVar("T")
14
15
16async def retry(operation: Callable[[], Awaitable[T]], attempts: int, delay: float) -> T:
17    """operation が ConnectionError で失敗した場合、delay 秒待って最大 attempts 回まで実行する。"""
18    for attempt in range(1, attempts + 1):
19        try:
20            return await operation()
21        except ConnectionError:
22            if attempt == attempts:
23                raise
24            await asyncio.sleep(delay)
25    raise ValueError("attempts には 1 以上を指定する")
26
27
28class FlakyServer:
29    """最初の failures 回だけ ConnectionError を送出するテスト用のサーバー。"""
30
31    def __init__(self, failures: int) -> None:
32        self.failures = failures
33        self.calls = 0
34
35    async def request(self) -> str:
36        self.calls += 1
37        await asyncio.sleep(0)
38        if self.calls <= self.failures:
39            raise ConnectionError("接続できない")
40        return "OK"
41
42
43class RetryTest(unittest.IsolatedAsyncioTestCase):
44    async def test_succeeds_after_failures(self) -> None:
45        server = FlakyServer(failures=2)
46        result = await retry(server.request, attempts=3, delay=0.01)
47        self.assertEqual(result, "OK")
48        self.assertEqual(server.calls, 3)
49
50    async def test_raises_when_attempts_run_out(self) -> None:
51        server = FlakyServer(failures=5)
52        with self.assertRaises(ConnectionError):
53            await retry(server.request, attempts=3, delay=0.01)
54        self.assertEqual(server.calls, 3)
55
56    async def test_finishes_within_time_limit(self) -> None:
57        server = FlakyServer(failures=1)
58        async with asyncio.timeout(1.0):  # テストが終わらなくなることを防ぐ
59            await retry(server.request, attempts=2, delay=0.01)
60
61
62if __name__ == "__main__":
63    unittest.main()

テストは次のコマンドで実行する。

python -m unittest test_retry.py

このサンプルのように、テストでは次の工夫をするとよい。

  • 外部のサーバーの代わりにテスト用のオブジェクトを使う。FlakyServer は、決まった回数だけ失敗するサーバーを模擬している。実際のネットワークを使わないため、テストの結果が安定する。

  • 待ち時間を短くする。delay=0.01 のように、テストでは待ち時間を短く指定し、テストの実行時間を抑える。

  • テストにもタイムアウトを設定する。不具合によってタスクが永久に待ち続けると、テストが終わらなくなる。asyncio.timeout() で上限を設けておく。

スレッドを使うコードのテストでは、競合状態がたまたま起きずにテストが通ってしまうことがある。共有データを扱うクラスは、ロックで保護されていることをコードレビューで確認し、多数のスレッドから繰り返し呼び出すテストも併用するとよい。
