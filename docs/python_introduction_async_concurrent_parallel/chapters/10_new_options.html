第 10 章 GIL を超える新しい選択肢

ここまでの章では、CPU バウンドな処理を並列に実行するにはプロセスが必要であると説明してきた。しかし、プロセスには起動の負荷やデータの受け渡しの負荷がある。この制約を解消するため、近年の Python には新しい仕組みが追加されている。この章では、free-threaded ビルドとサブインタプリタを紹介する。

どちらも比較的新しい機能であり、仕様や対応状況は今後のバージョンで変わる可能性がある。実際に使う場合は、使用する Python のバージョンの公式ドキュメントを確認してほしい。

free-threaded ビルド

free-threaded ビルド は、GIL を無効にした CPython である。PEP 703 で提案され、Python 3.13 で実験的に提供された後、Python 3.14 で正式にサポートされた（PEP 779）。free-threaded ビルドでは、複数のスレッドが Python のコードを本当に並列に実行できるため、CPU バウンドな処理もスレッドで速くなる。

free-threaded ビルドは、通常のビルドとは別に配布されている。実行ファイルの名前は python3.14t のように末尾に t が付く。Windows の Python install manager では py install 3.14t でインストールできる。

実行中の Python が free-threaded ビルドかどうかは、次のサンプルで確認できる。このサンプルは、CPU バウンドな処理を 4 つのスレッドで実行した場合と逐次処理の場合の経過時間も比べる。

check_gil.py

 7import sys
 8import sysconfig
 9import threading
10import time
11
12THREADS = 4
13LOOPS = 3_000_000
14
15
16def gil_status() -> str:
17    free_threaded_build = bool(sysconfig.get_config_var("Py_GIL_DISABLED"))
18    if sys.version_info >= (3, 13):
19        enabled = sys._is_gil_enabled()
20    else:
21        enabled = True  # 3.12 以前には free-threaded ビルドが無い
22    return f"free-threaded ビルド: {free_threaded_build}, GIL 有効: {enabled}"
23
24
25def cpu_task() -> None:
26    total = 0
27    for i in range(LOOPS):
28        total += i * i
29
30
31def main() -> None:
32    print(f"Python {sys.version.split()[0]}, {gil_status()}")
33
34    start = time.perf_counter()
35    for _ in range(THREADS):
36        cpu_task()
37    print(f"逐次: {time.perf_counter() - start:.2f} 秒")
38
39    start = time.perf_counter()
40    threads = [threading.Thread(target=cpu_task) for _ in range(THREADS)]
41    for thread in threads:
42        thread.start()
43    for thread in threads:
44        thread.join()
45    print(f"スレッド {THREADS} 個: {time.perf_counter() - start:.2f} 秒")
46
47
48if __name__ == "__main__":
49    main()

通常のビルドの Python 3.14 で実行すると、次のような結果になる。スレッドは逐次処理より遅い。

Python 3.14.6, free-threaded ビルド: False, GIL 有効: True
逐次: 1.14 秒
スレッド 4 個: 3.06 秒

free-threaded ビルドで実行すると、GIL 有効 が False になり、スレッドの数に応じて経過時間が短くなる。sysconfig.get_config_var("Py_GIL_DISABLED") は Python が free-threaded ビルドかどうかを、sys._is_gil_enabled() は実行中に GIL が有効かどうかを返す。free-threaded ビルドでも、GIL に対応していない C 拡張モジュールを import すると、GIL が自動的に有効になることがある。

free-threaded ビルドを使う場合は、次の点に注意する。

  • シングルスレッドの性能が少し下がる。参照カウントなどをスレッドセーフにするための処理が増えるためである。

  • C 拡張モジュールの対応が必要である。NumPy などの主要なライブラリは対応が進んでいるが、すべてのライブラリが対応しているわけではない。

  • スレッドセーフでないコードの問題が表面化しやすくなる。GIL があることで偶然動いていたコードが、競合状態によって誤動作することがある。第 5 章 スレッドによる並行処理 で説明したロックなどによる排他制御が、これまで以上に重要になる。

サブインタプリタ

サブインタプリタ は、1 つのプロセスの中に作られる、互いに独立した Python のインタプリタである。各サブインタプリタは独自のモジュールやグローバル変数を持ち、Python 3.12 以降ではそれぞれ独立した GIL を持つ（PEP 684）。そのため、通常のビルドの Python でも、サブインタプリタを使えば 1 つのプロセスの中で CPU バウンドな処理を並列に実行できる。

Python 3.14 では、サブインタプリタを Python のコードから使うための concurrent.interpreters モジュール（PEP 734）と、concurrent.futures.InterpreterPoolExecutor が追加された。InterpreterPoolExecutor は、ThreadPoolExecutor や ProcessPoolExecutor と同じ使い方で、タスクをサブインタプリタで実行する。

interpreter_pool.py

 7import math
 8import sys
 9import time
10
11LIMIT = 2_000_000
12CHUNKS = 16
13
14
15def is_prime(n: int) -> bool:
16    if n < 2:
17        return False
18    if n % 2 == 0:
19        return n == 2
20    for divisor in range(3, math.isqrt(n) + 1, 2):
21        if n % divisor == 0:
22            return False
23    return True
24
25
26def count_primes(start: int, stop: int) -> int:
27    """start 以上 stop 未満の素数の個数を返す。
28
29    sum(1 for n in ... if is_prime(n)) のように、ジェネレーター式の中からグローバルな関数を参照すると、
30    Python 3.14.6 の InterpreterPoolExecutor では NameError になるため、for 文で書いている。
31    """
32    count = 0
33    for n in range(start, stop):
34        if is_prime(n):
35            count += 1
36    return count
37
38
39def run_in_subinterpreters(starts: list[int], stops: list[int]) -> int:
40    if sys.version_info < (3, 14):
41        raise RuntimeError("InterpreterPoolExecutor は Python 3.14 以降で使用できる")
42    else:
43        from concurrent.futures import InterpreterPoolExecutor
44
45        with InterpreterPoolExecutor() as executor:
46            return sum(executor.map(count_primes, starts, stops))
47
48
49def main() -> None:
50    if sys.version_info < (3, 14):
51        print("このサンプルの実行には Python 3.14 以降が必要である。")
52        return
53
54    size = LIMIT // CHUNKS
55    starts = [i * size for i in range(CHUNKS)]
56    stops = [start + size for start in starts]
57
58    start = time.perf_counter()
59    total = sum(map(count_primes, starts, stops))
60    print(f"逐次: {total} 個, {time.perf_counter() - start:.2f} 秒")
61
62    start = time.perf_counter()
63    total = run_in_subinterpreters(starts, stops)
64    print(f"サブインタプリタ: {total} 個, {time.perf_counter() - start:.2f} 秒")
65
66
67if __name__ == "__main__":
68    main()

執筆環境では次の結果になった。第 6 章 プロセスによる並列処理 の prime_pool.py と同じ計算を、プロセスを使わずに並列に実行できている。

逐次: 148933 個, 5.93 秒
サブインタプリタ: 148933 個, 1.27 秒

このサンプルの run_in_subinterpreters() では、sys.version_info による分岐の中で InterpreterPoolExecutor を import している。Python 3.13 以前ではこのクラスが存在しないため、このように書くことで、古いバージョンでも import の時点でエラーにならず、mypy による型チェックも通る。

サブインタプリタを使う場合は、次の点に注意する。

  • データはサブインタプリタ間で共有されない。引数と戻り値は、プロセスと同じように pickle などでコピーして受け渡される。

  • サブインタプリタに対応していない C 拡張モジュールがある。対応していないモジュールをサブインタプリタの中で import すると、ImportError になる。

  • 関数の書き方によっては正しく動かない。執筆環境の Python 3.14.6 では、count_primes() を sum(1 for n in range(start, stop) if is_prime(n)) のようにジェネレーター式で書くと、サブインタプリタの中で NameError: name 'is_prime' is not defined が発生した。ジェネレーター式の中からだけグローバルな関数を参照していると、関数がグローバル変数を使わないものとして扱われ、関数が定義されたモジュールの名前空間を持たずにサブインタプリタへ渡されるためと考えられる。このサンプルでは for 文で書いて回避している。
